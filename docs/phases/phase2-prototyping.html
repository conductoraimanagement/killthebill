PHASE 2 Godot Prototyping

This phase represents the transition from architectural theory to engine execution. The goal is to establish the fundamental 3D environment, the isometric camera, and the player navigation systems in Godot 4.

DONE 2.1: Isometric Camera Rig

Objective: Establish the visual perspective of the immersive sim, giving the player a 'god-game' view of the systemic world.

Technical Breakdown:

  • Class: Custom Camera3D script (CameraController.gd).
  • Projection: Rigidly set to Orthogonal to create the classic retro-tactical isometric look, avoiding perspective distortion.
  • Transform Math: The camera's local rotation is mathematically locked to exactly X: -30 degrees, Y: 45 degrees.
  • Input Mechanics: Reads `get_viewport().get_mouse_position()` for edge-panning (moving the camera when the mouse hits screen borders), maps WASD for manual panning, and intercepts mouse-wheel events for Orthogonal size adjustment (zooming) bounded by predefined `min_zoom` and `max_zoom` clamps.
  • Player Tracking: Uses a mathematically smooth interpolation (lerp over delta time) to re-center on the `PlayerManager.current_avatar` when the spacebar is pressed or tracking is toggled on.

DONE 2.2: WorldDirector Expansion (PR & Reputation)

Objective: Initialize the core memory and systemic mathematical brain of the entire game.

Technical Breakdown:

  • Class: Autoload Singleton Node (WorldDirector.gd).
  • Global Dictionaries: Stores the global_economy (food prices, tension, security presence) and the complex oligarchs dictionary (wealth, paranoia, public_image, controversy_level, and recent_scandals array).
  • The Signal Bus: Implements the event_triggered(action, target) signal. Any node in the game can emit this. The WorldDirector catches it, runs the action through the Butterfly Effect matrix, alters the economy, and fires back a world_state_changed signal so UI and NPCs can instantly react.
  • Sector Dynamics: Local sector variables (like tension modifiers in "The Sinks") are mathematically derived continuously from the overarching `global_economy` numbers via _update_sector_dynamics().

DONE 2.3: Player Navigation & Movement

Objective: Allow smooth, pathfinding-based movement across the isometric grid.

Technical Breakdown:

  • Class: CharacterBody3D with an attached NavigationAgent3D node (PlayerController.gd).
  • Input Raycasting: On `_input(event)` corresponding to a Right-Click, the active Camera3D fires a `project_ray_normal()` physics raycast intersecting with the environment's Collision layer.
  • Vector Math: The exact `Vector3` intersection point is fed to `NavigationAgent3D.target_position`.
  • Velocity Loop: Inside `_physics_process()`, the script calculates the next path point, applies a fixed `SPEED` scalar to the normalized direction vector, and calls Godot 4's move_and_slide(). The character mesh uses `look_at()` with spherical linear interpolation (`slerp`) to physically rotate towards the destination cleanly.

DONE 2.4: Procedural Greyboxing (The Sinks)

Objective: Build a test environment capable of verifying pathfinding and camera occlusion without relying on manual editor placement.

Technical Breakdown:

  • Class: Node3D procedural generator (GreyboxTestScene.gd).
  • Mesh Generation: Programmatically instantiates a 50x50 `CSGBox3D` acting as the floor, and iterates through a nested loop to scatter CSGBox3D pillars representing brutalist architecture.
  • Dynamic Navmesh: A NavigationRegion3D wraps the generated meshes. The script triggers a runtime bake_navigation_mesh() so the PlayerController can immediately begin pathfinding around the procedurally generated obstacles as soon as the scene loads.
